## 📖 ภาพรวมระบบ (System Overview)

**IT VERTEX** คือระบบบริหารจัดการงานซ่อมคอมพิวเตอร์ โน้ตบุ๊ก ปริ้นเตอร์ และอุปกรณ์ไอที ออกแบบมาเพื่อเชื่อมโยงการทำงานระหว่าง **หน้าร้าน (Staff)**, **ช่างซ่อม (Technician)**, **ลูกค้า (Customer)** และ **ผู้จัดการ (Manager)** ให้ทำงานร่วมกันได้อย่างไร้รอยต่อ

### สถาปัตยกรรมระบบ (Architecture):
- **Frontend:** React Native (Expo SDK 54), Expo Router v6 (File-based Routing), NativeWind v4 (Tailwind CSS), Kanit Font
- **Backend API:** Node.js (Express REST API), JWT Authentication, Bcryptjs, Multer, Swagger UI (`/api-docs`)
- **Database:** PostgreSQL — **19 ตาราง + 1 view** (`repair_jobs_view`) พร้อม Master Data ครบ (ประเภทเครื่อง, ยี่ห้อ, รุ่น, ยี่ห้อ–ประเภทเครื่อง, อะไหล่/ค่าบริการ, สถานะ, บทบาท)
- **การแยกชั้นโค้ดฝั่ง Server:** คำสั่ง SQL ทั้งหมดอยู่ใน `back-end/queries/` ส่วน `controllers/` ทำหน้าที่ประกอบคำสั่งและจัดการ Business Logic เท่านั้น

### 1. มาตรฐานโค้ดทั้งระบบ (Code Standardization)
- เพิ่มเอกสารมาตรฐานกลาง **[STANDARD.md](./STANDARD.md)** — สรุปสถาปัตยกรรม ผังทุก flow การทำงาน (FLOW-xx) และมาตรฐานการเขียนโค้ดทั้ง Frontend / Backend (ISS-xx)
- **สีแดงแบรนด์ 3 เฉด รวมเหลือเฉดเดียว (`#DC2626`)** — ทุกหน้าจออ้างจาก `Colors.primary` ใน `constants/theme.ts` หรือโทเคน `primary` ของ Tailwind แทนการ hardcode (แก้ 279 จุด ใน 84 ไฟล์)
- **รวมระบบแจ้งเตือน/popup** ที่เดิมกระจัดกระจายใน 20 ไฟล์ มาใช้ hook กลาง `useAlert()` ตัวเดียว (`hooks/use-alert.tsx`) — กล่องข้อความ/กล่องยืนยันหน้าตาเดียวกันทุกหน้าจอ
- **SQL Layer:** ย้ายคำสั่ง SQL 107 คำสั่งที่ฝังใน controller ไปไว้ใน `back-end/queries/` (11 โมดูล) — controller เหลือเฉพาะการประกอบ clause
- **ค่าคงที่ (Constants):** เลิกใช้เลข Magic Number ในหน้าจอ ใช้ `constants/status.ts` (`REPAIR_STATUS`, `QUOTE_STATUS`, `ROLES`, `PAYMENT_METHODS`, `CANCEL_INSPECTION_FEE`) และ `back-end/constants/index.js` ให้ตรงกับตารางในฐานข้อมูล
- **แก้ชื่อโฟลเดอร์/กลุ่มเส้นทางที่สะกดผิด:** `Meneger_*` → `Manager_*`, `Technicain_*` → `Technician_*`, `(meneger)` → `(manager)`, `(technicain)` → `(technician)`
- **Backend:** จำกัด `POST/PUT/DELETE /api/items` ให้เฉพาะ Manager (เดิมบทบาทใดก็แก้ไขได้), ทำรหัสตอบกลับ (201 เมื่อสร้างข้อมูล) และชื่อฟังก์ชัน (`remove`) ให้เป็นแบบเดียวกันทั้งระบบ

### 2. แดชบอร์ดผู้จัดการและพนักงาน (Dashboard)
- **กราฟแนวโน้มรายได้** (`RevenueTrendChart`) — วาดเป็นเส้นโค้งเรียบ แสดงครบทุกวันของเดือน (วันที่ไม่มียอดขายแสดงเป็น 0 บนแกนล่าง) และคิด **ค่าเฉลี่ยจากเฉพาะช่วงที่มียอดจริง**
- **กำไรขั้นต้น (Gross Profit)** = รายรับรวม − ต้นทุนอะไหล่ โดยนับเฉพาะ **ใบเสนอราคาที่อนุมัติแล้ว** และใช้ต้นทุนที่ Snapshot ไว้ใน `quotation_details.unit_cost` ตั้งแต่วันที่ออกใบเสนอราคา
- **วันรับรู้รายได้** เรียงตามลำดับ `return_date` → `repaired_at` → `payment_date` → `created_at` (คำนวณตามเขตเวลา `Asia/Bangkok`)
- **ตัวกรองประเภทอุปกรณ์ดึงจากฐานข้อมูลจริง** ผ่าน `GET /api/catalog/device-types` (ไม่ Hardcode) พร้อมป้ายชื่อ/สัญลักษณ์ประเภทเครื่องที่ใช้ร่วมกันทุกกราฟใน `lib/deviceTypeLabel.ts`
- **ซ่อนข้อมูลรายได้ตามบทบาท (Role-based)** — บทบาท **Staff จะไม่เห็นรายได้ กำไร และต้นทุนอะไหล่** เลย โดยบังคับที่ฝั่ง Server จาก JWT (`req.user.role_name === 'manager'`) ไม่ใช่แค่ซ่อนบนหน้าจอ
- คอมโพเนนต์กราฟ: `RevenueTrendChart`, `RepairTrendChart`, `SymptomsChart` และ `WorkActivityChart`

### 3. ระบบแจ้งเตือนลูกค้า (`(customer)/notifications`)
- แจ้งเตือน **ครอบคลุมทุกเหตุการณ์สำคัญ** ของงานซ่อม โดยคำนวณจากข้อมูลงานซ่อมจริง (ไม่มีตารางแจ้งเตือนใหม่ในฐานข้อมูล)
  - ใบเสนอราคาส่งถึงลูกค้า → รอการอนุมัติ
  - **ลูกค้าตีกลับ/ขอแก้ไขใบเสนอราคา** (แจ้ง acknowledgement ของการตีกลับ) และ **พนักงานตีกลับการชำระเงิน**
  - **ใบเสร็จพร้อม** → แตะเพื่อเปิดหน้าใบเสร็จได้ทันที
  - **ยกเลิกซ่อม → แจ้งค่าตรวจเช็ค** (300 บาท) และกรณีปิดงานพร้อมชำระแล้ว
  - รอลูกค้าตรวจสอบ/ยืนยันการชำระเงิน
- จัดเรียงใหม่ → เก่า โดยใช้เวลาจากการเคลื่อนไหวล่าสุดของงาน (`last_action_at`)

### 4. หน้ารับเครื่อง: ยกเลิกการสร้างลูกค้าโดยพนักงาน
- พนักงาน **ไม่สามารถสร้างบัญชีลูกค้าใหม่ได้แล้ว** — ต้องค้นหาลูกค้าที่มีอยู่ในระบบ (ด้วยชื่อ / เบอร์โทร / อีเมล)
- ถ้าไม่พบลูกค้า ระบบจะแจ้งให้ลูกค้า **สมัครบัญชีเอง** ที่หน้า Register ของแอป แล้วจึงกลับมาทำรายการรับเครื่อง

### 5. หน้าตรวจสอบการชำระเงิน (verify-payment)
- ยืนยันการชำระเงินได้ตามปกติ (แก้บั๊กเดิมที่ไม่สามารถยืนยันได้)
- **กด "ปฏิเสธ" แล้วกลับไปหน้าก่อนหน้าอัตโนมัติ** เพื่อรอลูกค้าส่งสลิปใหม่ และระบบตั้งสถานะงานกลับเป็น `รอชำระ`

### 6. ลบแนวคิด "วันนัดรับเครื่อง" ออกจากทั้งระบบ
ระบบเหลือวันที่ที่ใช้งานจริงเพียง 2 วัน

| ชื่อวันที่ในระบบ | คอลัมน์ฐานข้อมูล | ถูกบันทึกเมื่อไหร่ |
|---|---|---|
| **วันรับเครื่องมา** | `repair_job.created_at` | ตอนพนักงานเปิดใบรับซ่อมที่หน้าร้าน |
| **วันรับเครื่องคืน** | `repair_job.return_date` | ตอนลูกค้าเซ็นรับเครื่องคืนที่ร้าน |

- **ฐานข้อมูล:** ลบคอลัมน์ `repair_job.appointment_date` และสร้าง `repair_jobs_view` ใหม่ที่ไม่มีคอลัมน์นี้
- *(หน้า `schedule-pickup` เหลือไว้แสดงปฏิทินวันเปิดร้านเท่านั้น ไม่ใช่การนัดหมาย)*

### 7. ทำความสะอาดฐานข้อมูล (Database Cleanup)
- ลบข้อมูลค้าง/พังออกจากฐานข้อมูล (ใบซ่อมทดสอบที่ใช้อะไหล่ทดสอบ, ใบซ่อมที่ข้อมูลการชำระเงินขัดกับสถานะงาน, อะไหล่ทดสอบ และ Token ค้าง) ให้เหลือเฉพาะข้อมูลที่ใช้งานจริง
- สำรองฐานข้อมูลก่อนลบไว้ที่โฟลเดอร์ `back-end/_backup/`

### 8. สคริปต์ฐานข้อมูล 2 แบบ + แก้สคริปต์ติดตั้งให้รันได้จริง
- เพิ่ม **`back-end/mockup.sql`** — สร้างโครงสร้างครบเหมือน `database.sql` แต่ใส่ **เฉพาะ Master Data** (ไม่มีบัญชีผู้ใช้/งานซ่อม) เหมาะกับการเริ่มฐานข้อมูลใหม่แบบสะอาด
- แก้ `database.sql` ให้ **import แล้วใช้งานได้จริง**: เติมตาราง **`brand_device_types`** (ยี่ห้อ ↔ ประเภทอุปกรณ์) ที่เดิมตกหล่น พร้อมประเภทเครื่อง `Tablet / iPad` และยี่ห้อที่เพิ่มใหม่ (26–30) ให้ครบตามฐานข้อมูลจริง

## 👥 บทบาทผู้ใช้งานในระบบ (User Roles & Permissions)

| **ผู้จัดการ (Manager)** | ดูแดชบอร์ดภาพรวม สถิติงานซ่อม รายได้ กำไรขั้นต้น (รายรับ − ต้นทุนอะไหล่), จัดการข้อมูลอะไหล่/บริการ, อุปกรณ์ (ประเภท/ยี่ห้อ/รุ่น) และจัดการข้อมูลพนักงานในระบบ |

## 🚀 ขั้นตอนการติดตั้งและรันระบบ (Step-by-Step Installation)

### ขั้นตอนที่ 1: ตั้งค่าฐานข้อมูล PostgreSQL

1. เปิดโปรแกรม **pgAdmin 4** หรือใช้งานผ่าน Terminal / PowerShell ด้วย `psql`
2. สร้างฐานข้อมูลใหม่ชื่อ **`app_data`**:
   ```sql
   CREATE DATABASE app_data;
   ```
3. เลือกไฟล์สคริปต์ที่ต้องการนำเข้า (Import) จากโฟลเดอร์ `back-end/`:

   | ไฟล์ | โครงสร้าง | ข้อมูลที่ใส่ให้ | เหมาะกับ |
   |---|---|---|---|
   | **`database.sql`** | 19 ตาราง + view + index | Master Data ครบ + **บัญชีทดสอบ 4 บทบาท** | ติดตั้งเพื่อพัฒนา/เดโม **(แนะนำ)** |
   | **`mockup.sql`** | 19 ตาราง + view + index (เหมือนกันเป๊ะ) | **เฉพาะ Master Data** — ไม่มีบัญชีผู้ใช้และไม่มีงานซ่อม | เริ่มฐานข้อมูลใหม่แบบสะอาด / ส่งมอบงาน |

   - **วิธีที่ 1 (ผ่าน Terminal / Command Prompt):**
     ```bash
     # เข้าไปที่โฟลเดอร์ back-end
     cd back-end

     # รันคำสั่ง psql เพื่อ import ข้อมูล (ระบบจะถามรหัสผ่านของ postgres)
     psql -U postgres -d app_data -f database.sql
     ```
   - **วิธีที่ 2 (ผ่าน pgAdmin 4):**
     - เปิด pgAdmin 4 -> เชื่อมต่อ Database Server
     - คลิกขวาที่ฐานข้อมูล `app_data` -> เลือก **Query Tool**
     - เปิดไฟล์ `back-end/database.sql` คัดลอกคำสั่งทั้งหมดมาวาง
     - กดปุ่ม **Execute (F5)** เพื่อรันสคริปต์

   > ⚠️ **คำเตือน:** ทั้งสองไฟล์เริ่มต้นด้วยการ `DROP TABLE` ของเดิมทั้งหมด — **ห้ามรันกับฐานข้อมูลที่มีข้อมูลจริง** เพราะข้อมูลจะหายทั้งหมด (ให้ใช้กับฐานข้อมูลใหม่หรือฐานข้อมูลเดโมเท่านั้น)

4. *หมายเหตุ:* ในไฟล์ `database.sql` มีโครงสร้างตาราง ข้อมูล Master Data ครบถ้วน (ประเภทเครื่อง, ยี่ห้อ, รุ่น, **การผูกยี่ห้อกับประเภทเครื่อง**, อะไหล่, ค่าบริการ, สถานะงาน, บทบาท) พร้อมทั้ง **บัญชีผู้ใช้งานทดสอบ (Profiles) ทั้ง 4 บทบาท** ไว้ให้พร้อมใช้งานทันที โดย **ไม่มีข้อมูลงานซ่อมค้าง** เพื่อให้ผู้ทดสอบสามารถจำลองกระบวนการทำงานจริงตั้งแต่เปิดงานซ่อมใหม่ได้ด้วยตนเองอย่างสมบูรณ์

### ขั้นตอนที่ 2: ติดตั้งและรัน Backend API

   ```bash

   ```
2. ติดตั้ง Dependencies:
   ```bash
   npm install
   ```
3. ตรวจสอบหรือสร้างไฟล์ `.env` ที่โฟลเดอร์ `back-end/.env`:
   ```env
   DB_USER=postgres
   DB_PASSWORD=******
   DB_HOST=localhost
   DB_PORT=5432
   DB_NAME=app_data
   JWT_SECRET=*********
   PORT=3002
   ```
   *(แก้ไข `DB_PASSWORD` ให้ตรงกับรหัสผ่าน PostgreSQL บนเครื่องของคุณ)*

4. สตาร์ต Backend Server:
   ```bash
   # โหมด Development (Auto reload)
   npm run dev

   # หรือรันปกติ
   npm start
   ```
5. เมื่อรันสำเร็จ จะแสดงข้อความ:
   ```text

     ║   Swagger:    http://localhost:3002/api-docs ║
     ╚══════════════════════════════════════════╝
   ```
   - ตรวจสอบว่า API ทำงานได้ที่ `http://localhost:3002` (จะตอบ `{ "success": true, "message": "IT VERTEX API is running" }`)
   - เอกสาร API (Swagger UI) อยู่ที่ `http://localhost:3002/api-docs`

## 🎬 คู่มือการจำลอง Flow การทำงานตั้งแต่ต้นจนจบ (Simulation Guides)

คุณสามารถทดสอบวงจรการทำงานจริงของร้านซ่อมได้ตามลำดับดังนี้ (สถานะงานซ่อมมี 9 สถานะ ตาม `constants/status.ts`)

### 1️⃣ ขั้นตอนที่ 1: พนักงานรับเครื่องซ่อมหน้าร้าน (Staff)
1. ออกจากระบบ (หากล็อกอินอยู่) แล้วล็อกอินด้วยบัญชี **Staff** (`staff1@gmail.com`)
2. กดแท็บ **"รับเครื่อง"** (`/receive`) ด้านล่าง
3. **ค้นหาลูกค้าเดิม** ด้วยชื่อ / เบอร์โทร / อีเมล (เช่น `ลูกค้า ใจดีที่สุด`)
   - ⚠️ **พนักงานสร้างลูกค้าใหม่ไม่ได้แล้ว** (ยกเลิกการสร้างลูกค้าโดยพนักงาน) — ถ้าไม่พบลูกค้า ให้ลูกค้าสมัครบัญชีเองที่หน้า **Register** ของแอปก่อน แล้วกลับมาทำรายการใหม่
4. กรอกข้อมูลอุปกรณ์:
   - เลือก **ประเภทอุปกรณ์** (เช่น Notebook / Laptops) — ตัวเลือกดึงจากฐานข้อมูล
   - เลือก **ยี่ห้อ (Brand)**: ลิสต์จะเหลือเฉพาะยี่ห้อที่ขายในประเภทเครื่องที่เลือก
   - เลือก **รุ่น (Model)**: เลือกจากลิสต์ หรือพิมพ์ระบุรุ่นเองได้
   - ระบุอาการเสียที่ลูกค้าแจ้ง (เช่น *เปิดเครื่องติดแต่ไม่ขึ้นภาพ*)
5. กดปุ่ม **"ตรวจสอบข้อมูลและออกใบรับเครื่อง"** -> ตรวจสอบตัวอย่างใบรับซ่อม -> กดยืนยัน
6. งานซ่อมใหม่จะถูกบันทึกเข้าสู่ระบบในสถานะ **`รอตรวจเช็ค`** (Job ID เช่น `REP-xxxxxx`)

---

### 2️⃣ ขั้นตอนที่ 2: ช่างตรวจเช็คและทำใบเสนอราคา (Technician)
1. สลับบัญชีเข้าสู่ระบบด้วย **Technician** (`technician1@gmail.com`)
2. แท็บ **"รายการซ่อม"** จะพบงานซ่อมใหม่ที่เพิ่งรับเข้ามา
3. กดเข้าไปดูรายละเอียด -> เปลี่ยนสถานะเป็น **`ดำเนินการตรวจเช็ค`** (แท็บ "ตรวจเช็ค")
4. เมื่อตรวจเช็คเสร็จ ไปที่แท็บ **"ใบเสนอราคา"** -> สร้างใบเสนอราคา (`/make-quote`)
5. ระบุ **อาการเสียจริงที่ตรวจพบ** (เช่น *แรมเสีย หรือ เมนบอร์ดช็อต*)
6. เลือกรายการ **อะไหล่** และ **ค่าบริการ** จากระบบ (ระบบคำนวณยอดรวมค่าซ่อมให้อัตโนมัติ)
7. กด **"บันทึกและส่งใบเสนอราคา"** -> ยืนยันการส่ง (สถานะงาน: `ดำเนินการเสนอราคา` -> `รอการอนุมัติ`)
8. ระบบแจ้งเตือนลูกค้าทันทีที่หน้า **"แจ้งเตือน"** ของลูกค้า

---

### 3️⃣ ขั้นตอนที่ 3: ลูกค้าตรวจสอบและตอบใบเสนอราคา (Customer)
1. สลับบัญชีเข้าสู่ระบบด้วย **Customer** (`cus1@gmail.com`)
2. ลูกค้าจะเห็นงานที่อยู่ในสถานะ **`รอการอนุมัติ`** (มีแจ้งเตือนที่แท็บ "แจ้งเตือน")
3. กดดูรายละเอียดใบเสนอราคา ลูกค้าสามารถเลือก:
   - **อนุมัติการซ่อม:** ยืนยันอนุมัติ -> สถานะงานเปลี่ยนเป็น **`อนุมัติแล้ว/รอซ่อม`**
   - **ขอแก้ไข (ตีกลับ):** ระบุหมายเหตุ -> งานกลับไปสถานะ **`ดำเนินการเสนอราคา`** ให้ช่างแก้ไข และลูกค้าจะได้รับแจ้งเตือนว่าใบเสนอราคาถูกตีกลับแล้ว
   - **ยกเลิกซ่อม:** หากไม่ต้องการซ่อม -> สถานะ **`ยกเลิกซ่อม`** (คิดเฉพาะค่าตรวจเช็คมาตรฐาน 300 บาท)

---

### 4️⃣ ขั้นตอนที่ 4: ช่างดำเนินการซ่อม (Technician)
1. สลับกลับมาที่บัญชี **Technician**
2. เมื่อเห็นงานอยู่ในสถานะ **`อนุมัติแล้ว/รอซ่อม`** กดรับงานเพื่อซ่อมจริง
3. เมื่อซ่อมเสร็จเรียบร้อย เปลี่ยนสถานะเป็น **`รอชำระ`** เพื่อให้ลูกค้าชำระเงิน
4. ฝั่งลูกค้า: เปิดงานในรายการซ่อม -> **อัปโหลดสลิปการชำระเงิน** (สถานะงานยังเป็น `รอชำระ`)

---

### 5️⃣ ขั้นตอนที่ 5: หน้าร้านตรวจสอบการชำระเงินและส่งมอบเครื่อง (Staff)
1. สลับบัญชีเข้าสู่ระบบด้วย **Staff**
2. ไปที่แท็บ **"ส่งมอบ"** (`/deliver`) หรือ **"รายการซ่อม"** จะพบงานที่อยู่ในหมวด **`รอชำระ`**
3. กดปุ่ม **"ตรวจชำระ"** เพื่อตรวจสอบสลิป แล้วเลือก:
   - **ยืนยันการชำระเงิน** -> สถานะงานเปลี่ยนเป็น **`รอลูกค้ามารับเครื่อง`**
   - **ปฏิเสธการชำระเงิน** -> ระบบกลับไปหน้าก่อนหน้าโดยอัตโนมัติ และตั้งสถานะกลับเป็น **`รอชำระ`** เพื่อรอลูกค้าส่งสลิปใหม่ (ลูกค้าจะได้รับแจ้งเตือนให้ส่งใหม่)
4. เมื่อลูกค้ามารับเครื่อง: กดปุ่ม **"ส่งมอบ"** (`/deliver-handover`)
5. ตรวจสอบรายการและให้ลูกค้า **เซ็นชื่อรับเครื่องแบบดิจิทัล (Digital Signature)** บนหน้าจอ
6. กดยืนยันส่งมอบ -> สถานะงานจะเปลี่ยนเป็น **`เสร็จสิ้น`** พร้อมพิมพ์ใบเสร็จรับเงินให้ลูกค้าได้ทันที (ลูกค้าได้รับแจ้งเตือนว่าใบเสร็จพร้อมแล้ว และเปิดดูได้จากแท็บแจ้งเตือน)

---

### 6️⃣ ขั้นตอนที่ 6: ผู้จัดการตรวจสอบภาพรวมและบริหารจัดการ (Manager)
1. ล็อกอินด้วยบัญชี **Manager** (`Manager1234@gmail.com`)
2. หน้า **"ภาพรวม"**: ดูกราฟยอดขาย/แนวโน้มรายได้ สถิติจำนวนงานซ่อม และรายได้รวมของร้าน (พร้อมกำไรขั้นต้น)
3. หน้า **"อะไหล่"**: ตรวจสอบรายการอะไหล่และค่าบริการ เพิ่ม/แก้ไขราคาขายและต้นทุนได้
4. หน้า **"อุปกรณ์"**: จัดการประเภทเครื่อง ยี่ห้อ รุ่น และการผูกยี่ห้อกับประเภทเครื่อง
5. หน้า **"พนักงาน"**: จัดการข้อมูลพนักงานและช่างซ่อมในร้าน

## 📏 มาตรฐานการเขียนโค้ดและสถาปัตยกรรม (Coding Standard)

รายละเอียดทั้งหมดอยู่ใน **[STANDARD.md](./STANDARD.md)** — สรุปสาระสำคัญ:

| หัวข้อ | มาตรฐานที่ใช้ |
|---|---|
| รูปแบบข้อความตอบกลับ API | `{ success, data?, message? }` (สร้างข้อมูลสำเร็จใช้ `201`) |
| สิทธิ์การเข้าถึง | ตรวจที่ `routes/` ด้วย `role('Manager', 'Staff', ...)` + ตรวจ JWT ที่ `middleware/` |
| คำสั่ง SQL | อยู่ใน `back-end/queries/` เท่านั้น — `controllers/` ห้ามเขียน SQL เต็มประโยค |
| จัดการ Error | ทุก controller ใช้ `try/catch` แล้วส่งต่อ `next(err)` ให้ Central Error Handler |
| Frontend เรียก API | ผ่าน `lib/api.ts` เท่านั้น (`api.get/post/put/patch/del`) |
| แจ้งเตือน/popup | ใช้ hook กลาง `useAlert()` (`hooks/use-alert.tsx`) |
| สีและฟอนต์ | อ้างจาก `constants/theme.ts` (`Colors.primary = #DC2626`) หรือโทเคน `primary` ของ Tailwind — ห้าม hardcode |
| สถานะ/บทบาท | ใช้ค่าคงที่จาก `constants/status.ts` (Frontend) และ `back-end/constants/index.js` (Backend) |

## 🛠️ การแก้ปัญหาที่พบบ่อย (Troubleshooting)

### 1. Backend เชื่อมต่อฐานข้อมูลไม่ได้ (Database Connection Error)
- **สาเหตุ:** ข้อมูลใน `back-end/.env` ไม่ตรงกับเครื่องของคุณ หรือ Service PostgreSQL ยังไม่ได้เปิด
- **วิธีแก้:**
  - ตรวจสอบว่า Service PostgreSQL บน Windows กำลังทำงานอยู่ (เปิด Task Manager -> Services -> ดู `postgresql-x64`)
  - ตรวจสอบ `DB_PASSWORD` และ `DB_PORT` ในไฟล์ `back-end/.env` ให้ถูกต้อง

### 2. เจอ error `relation "brand_device_types" does not exist` (หรือหน้ารับเครื่องดึงยี่ห้อไม่ได้)
- **สาเหตุ:** ฐานข้อมูลถูกสร้างจากสคริปต์เวอร์ชันเก่าที่ตกหล่นตาราง `brand_device_types`
- **วิธีแก้:** Import `back-end/database.sql` (หรือ `mockup.sql`) เวอร์ชันล่าสุดลงฐานข้อมูลใหม่อีกครั้ง

### 3. Frontend ไม่สามารถดึงข้อมูลจาก Backend ได้ (Network Request Failed)
- **วิธีแก้:**
  - ตรวจสอบว่า Backend กำลังรันอยู่ที่พอร์ต `3002` และไม่มี Error
  - หากทดสอบบน **Web Browser:** ให้เข้าผ่าน `http://localhost:8081`
  - หากทดสอบบน **มือถือผ่าน Expo Go:** ต้องไม่ใช้ `localhost` ให้ระบุ IP Address ของคอมพิวเตอร์ใน `.env` เช่น `EXPO_PUBLIC_API_URL=http://192.168.1.XX:3002/api` (มือถือและคอมพิวเตอร์ต้องอยู่ Wi-Fi เดียวกัน)

### 4. พอร์ต 3002 หรือ 8081 ถูกใช้งานอยู่ (Port Already in Use)
- **วิธีแก้:** ปิดโปรเซสที่ค้างอยู่ หรือเปลี่ยนพอร์ตในไฟล์ `.env` ของ Backend เป็นพอร์ตอื่น เช่น `3003`

### 5. ล็อกอินไม่ผ่านทั้งที่กรอกรหัสถูก
- **วิธีแก้:** ตรวจสอบว่าไม่มีช่องว่างหน้า/หลังอีเมล และสังเกตกฎรหัสผ่านคือ **อีเมล + `Z`** (ยกเว้น Manager ที่รหัสผ่านพิมพ์ตกตัว `l` — ดูหัวข้อบัญชีทดสอบ) หากยังไม่ผ่านให้ตรวจว่าบัญชีนั้นมีอยู่จริงในตาราง `profiles`

### 6. หน้าจอไม่อัปเดตข้อมูล / แคชค้าง
- **วิธีแก้:** รีสตาร์ต Expo Dev Server แบบล้างแคช `npm start -- --clear` แล้วรีเฟรชเบราว์เซอร์หรือแอปอีกครั้ง
